# QA compare 웹 서비스

입력 하나에서 AST를 만들거나 Ver.A와 Ver.B를 비교하는 Streamlit 서비스다. Python 3.12 이상, Streamlit 1.64.0을 사용한다. 현재 Cloud 배포는 Python 3.12로 고정한다.

## 실행

```powershell
cd C:\codes\QA_train\streamlit
uv sync
.\run_qa_web.ps1
```

브라우저에서 http://127.0.0.1:8501 을 연다. 포트 변경은 `run_qa_web.ps1 -Port 8502`로 지정한다. macOS/Linux에서는 streamlit 폴더에서 `uv run streamlit run streamlit_app.py --server.address 127.0.0.1`로 실행한다.

## Streamlit Cloud

[QA compare 접속](https://apptrain-akecrcbajuvarqhr2dgtcs.streamlit.app/). 로컬 PC를 꺼도 접속할 수 있다.

- 저장소: `rupria/QA_train`, 브랜치: `main`, 실행 파일: `streamlit/streamlit_app.py`
- Python: 3.12, 의존성: `streamlit/uv.lock`
- Advanced settings / Secrets: `QA_WEB_ALLOW_LOCAL = "0"`
- Cloud에서는 서버의 로컬 경로를 입력하지 않고 파일 업로드·공개 GitHub HTTPS 입력을 사용한다.
- 작업 파일은 세션별로 분리되며 영구 저장을 보장하지 않는다. 다른 PC로 옮길 결과는 Markdown·JSON·ZIP으로 다운로드한다.

## 화면 구분

| 탭 | 목적 | 필요한 입력 |
|---|---|---|
| 비교 | Ver.A·Ver.B 변경과 QA 영향 후보 | 두 버전 |
| AST 연결·해석 | 변경 심볼의 연결과 값 흐름 | 완료한 코드 영향 비교 |
| 스냅샷 | 준비한 입력의 파일 목록·출처·보관 | 준비된 입력 |
| _AST (맨 오른쪽) | Python AST·프로젝트 파일 트리 생성 | 소스 하나 또는 커밋 하나 |

## 단일 AST 생성

1. 맨 오른쪽 **_AST** 탭을 연다.
2. `.py`, `.ipynb`, 프로젝트 ZIP, Git 커밋 하나 또는 준비된 Python 소스를 선택한다. 로컬 실행에서 허용한 경우 서버 PC의 경로도 가능하다. APK·IPA와 Python 원본이 없는 입력은 단일 AST 분석에 사용할 수 없다.
3. ZIP·저장소·폴더의 **분석 루트**를 지정한다. 전체는 `.`이다. Git은 **브랜치 목록 불러오기**로 브랜치를 선택한 뒤 **커밋 목록 불러오기**를 누른다. 선택한 브랜치의 최신 커밋이 기본값이며, 태그·해시 등은 **직접 입력**할 수 있다.
4. **AST 생성**을 누른다. 비교 입력을 추가로 지정할 필요가 없다.
5. **프로젝트 파일 트리**에서 폴더 계층과 데이터·설정·리소스 파일을 확인한다. **파일 선택**에서 상대 경로를 고르면 종류·크기·언어가 표시되고 **파일 식별 정보**에 SHA-256이 나온다. Python 파일은 아래 AST 표시와 연결되며, 노트북은 해당 파일의 코드 셀을 선택한다.
6. **트리형 / 정리형**으로 결과를 선택한다. 트리형은 선택한 파일·코드 셀의 `ast.dump(tree, indent=2)` 계층을 유지한다. 정리형에는 프로젝트 전체의 함수·클래스·호출·변수 대입과 원본 줄을 표시한다.
7. `ast_tree.md`, `file_tree.md`, `ast_structure.md`, `ast_structure.json` 또는 모두 포함한 `ast_reports.zip`을 내려받는다. 로컬 기본 저장 위치는 `.web_runs/session-<ID>/ast_reports/<run-ID>/`이며, `QA_WEB_WORKSPACE`를 지정하면 해당 작업 루트 아래에 저장한다.

파일 트리는 선택한 분석 루트에 준비된 스냅샷의 파일로 만든다. 빈 폴더와 제외된 캐시·빌드·Git 메타데이터는 포함하지 않으며, 제외된 항목은 **분석 범위·확인 사항**에서 확인한다. 데이터·설정 파일은 경로·종류 확인용이고 코드와의 실제 읽기·쓰기 연결을 추론하지 않는다. JSON의 `files`에는 상대 경로·종류·크기·SHA-256과 대응하는 `ast_paths`가 기록된다. `file_tree.md`는 폴더 계층만 별도로 보관하며 Python AST 트리 문서와 구분한다.

파싱 오류는 파일·셀 위치와 함께 같은 보고서에 기록하고, 일부 실패 또는 분석할 코드 셀이 없는 입력은 완료로 표시하지 않는다. 노트북은 Jupyter 전용 구문을 제외한 Python 본문을 분석하며 전처리 여부를 안내한다. `.py`는 인코딩 선언을 따른다. 트리 Markdown에는 원본 코드나 해설 표를 섞지 않는다.

입력 변경 시 이전 결과와 다운로드를 숨긴다. 탭 이동·결과 형식·표시할 파일 변경은 재분석하지 않는다. 생성한 소스 스냅샷은 현재 세션의 준비된 입력으로 재사용할 수 있다. 보고서 4개의 합계가 100MiB를 넘으면 분석 루트를 줄여야 한다. 화면의 개별 AST·파일 트리는 앞 262,144자까지 표시하며 전체 결과는 다운로드에 포함한다.

## 비교 사용 순서

1. 기본 **비교** 화면의 왼쪽 **Ver.A**, 오른쪽 **Ver.B**에서 각각 파일 업로드·Git·로컬 경로·준비된 입력 중 하나를 선택한다. 양쪽 입력 방식은 달라도 된다. 예를 들어 Git 커밋과 로컬 소스를 비교할 수 있다.
2. 각 입력의 파일·경로·버전을 지정하고 공통 설정에서 비교 방식, 필요한 기능·TC 매핑 JSON과 분석 깊이를 정한다. Git 브랜치·커밋 목록 조회는 버전을 고르기 위한 읽기 작업이며 이 단계에서 입력 변환이나 분석을 실행하지 않는다. Ver.A와 Ver.B에는 서로 다른 저장소 URL을 지정할 수 있다.
3. **두 입력 비교**를 한 번 누른다. 두 입력을 스냅샷으로 준비하고 분석한 결과를 같은 화면 아래에 표시한다. 입력·매핑·설정을 바꾸면 이 버튼으로 다시 실행해야 결과와 다운로드가 표시된다.
4. Python 코드 영향 비교라면 **AST 연결·해석** 탭에서 변경 지점과 추적 깊이를 고르고 **흐름 해석**을 누른다. Ver.A·Ver.B의 정적 값 전달 경로, 연결 차이와 코드 근거를 확인한다.
5. **스냅샷** 탭에서 파일 목록·출처를 확인하고 manifest 또는 보관용 ZIP을 내려받는다. 탭 이동은 업로드·입력·매핑을 보존하며 변환·분석을 새로 실행하지 않는다.

## 입력 방법

- 업로드: `.py`, `.ipynb`, `.apk`, `.ipa`, 프로젝트 `.zip`. 폴더는 ZIP으로 압축한다. 업로드당 최대 200MiB.
- 프로젝트 ZIP: 내부 비교 루트를 지정할 수 있다. `project/Assets`처럼 ZIP 안의 실제 경로를 사용한다. 서로 같은 프로젝트 기준을 선택한다.
- Git: 공개 GitHub 저장소 URL 또는 로컬 Git 저장소 경로를 입력하고, 브랜치와 커밋을 차례로 선택한다. GitHub는 `https://github.com/owner/repository` 형식을 익명으로 조회하며 인증정보가 포함된 URL은 지원하지 않는다. 브랜치 목록은 `ls-remote`로 ref만 읽으므로 이 단계에서 소스를 복제하지 않는다. 분석을 실행하면 별도 bare 저장소로 가져오고 선택한 버전을 고정 커밋 SHA로 준비한다. 기존 로컬 checkout은 변경하지 않는다. Git 실행 파일이 필요하다.
- 로컬 경로: Streamlit **서버 PC**의 파일·폴더를 읽는다. 브라우저 PC의 경로와 다를 수 있다. Git의 미커밋 파일까지 비교하려면 해당 작업 폴더를 로컬 소스로 준비한다.
- 준비된 입력: 현재 브라우저 세션에서 이미 만든 스냅샷을 선택해 다시 사용한다.
- 기능 매핑 JSON: 제품의 실제 기능 진입점과 TC ID를 작성한 파일을 공통 분석 설정에서 올린다. 매핑 없이 제품 기능명을 확정하지 않는다.

## Git 커밋을 골라 비교하기

1. **비교** 화면의 양쪽 입력 방식을 각각 **Git**으로 선택하고 공개 GitHub URL 또는 로컬 저장소 경로를 입력한다.
2. 각 칸에서 **브랜치 목록 불러오기**를 누르고 저장소의 기본 브랜치 또는 원하는 브랜치를 선택한다. 같은 저장소 주소는 Ver.A·Ver.B·`_AST`가 조회 결과를 공유하므로 같은 목록을 두 번 가져오지 않아도 된다. 서로 다른 저장소 주소는 각 칸에서 독립적으로 조회한다.
3. **커밋 목록 불러오기**를 누른다. 선택한 브랜치의 첫 부모 이력을 따라 최근 커밋을 최대 50건 조회한다. 이 버튼은 커밋 정보만 조회한다.
4. 날짜·커밋 메시지·짧은 SHA를 확인하며 각 칸에서 커밋을 선택한다. 왼쪽은 목록의 두 번째 커밋, 오른쪽은 첫 번째 커밋을 기본 선택하므로 같은 기준으로 조회하면 첫 부모와 최신 커밋을 비교한다. 이전 커밋이 없는 목록에서는 첫 커밋을 표시하며, 동일한 커밋과 비교 루트끼리는 비교할 수 없다.
5. 각 칸의 **저장소 내부 비교 루트**를 프로젝트 범위에 맞춘다. 전체 저장소는 `.`을 사용한다. 서로 다른 저장소는 폴더 구조가 다를 수 있으므로 실제 비교하려는 모듈에 맞게 각각 지정한다.
6. 공통 비교 설정을 확인하고 **두 입력 비교**를 누른다. 두 버전의 스냅샷을 만들고 분석한 결과가 같은 화면 아래에 표시된다. Python 소스는 코드 영향 분석을 지원하고, 그 밖의 원본 프로젝트는 파일 구성으로 비교한다.

목록에 없는 태그·커밋 SHA·`HEAD~1` 같은 ref는 각 Git 칸의 **직접 입력**에서 지정한다. 준비된 입력은 커밋 SHA로 고정되므로 이후 브랜치가 바뀌어도 같은 스냅샷을 비교한다.

Git은 한쪽에만 선택해도 된다. 다른 쪽에는 업로드한 소스, 로컬 소스 또는 준비된 원본 소스 입력을 지정할 수 있다. 일부 파일이 누락되는 등 입력 준비에 확인 사항이 있으면 분석 대신 해당 안내를 확인한다.

결과의 변경 파일 목록에서 파일을 고르면 텍스트 내용의 차이를 확인할 수 있다. UTF-8 텍스트만 표시하며, 파일당 512KiB·한 번의 비교에서 읽는 내용 합계 2MiB를 넘거나 바이너리이면 파일 구성·해시 변경과 안내를 표시한다. 긴 차이는 파일당 앞 131,072자까지 표시한다. 보고서 JSON과 Markdown에도 이 내용과 표시 한계를 함께 담는다.

## 기능·TC 매핑 JSON

최상위 JSON 객체에 `features` 배열을 작성한다. 배열의 각 항목은 하나의 제품 기능이며 다음 필드를 사용한다.

| 필드 | 형식과 작성 기준 |
|---|---|
| `id` | 필수 문자열. 기능을 구분하는 고유 ID이며 중복될 수 없다. |
| `name` | 필수 문자열. 제품에서 사용하는 기능명이다. |
| `entry_points` | 필수 배열. 해당 기능의 코드 진입점을 하나 이상 지정한다. 각 항목은 `file`과 `symbol` 문자열을 가진 객체다. |
| `entry_points[].file` | 비교 루트를 기준으로 한 실제 파일의 상대 경로다. 경로 구분자는 `/`를 사용한다. |
| `entry_points[].symbol` | 해당 파일에 선언된 실제 함수·클래스·메서드 등의 심볼 이름이다. 중첩된 심볼은 분석 결과의 이름과 일치시킨다. |
| `tc_ids` | 선택 문자열 배열. 해당 기능과 연결할 기존 TC ID를 작성한다. 생략하면 연결된 TC ID가 없는 것으로 처리한다. |

`id`와 `name`은 비어 있을 수 없다. 두 입력에서 선택한 비교 루트와 매핑의 파일 경로를 맞추고, 단일 파일의 이름이 서로 다르면 Ver.B 입력의 파일명을 기준으로 작성한다. 코드에서 확인되지 않은 진입점은 확인 사항으로 표시된다. 연결된 기능·TC는 정적 분석에 따른 검증 후보이며 실제 테스트 실행 결과가 아니다.

## AST 연결·해석

**흐름 해석**은 현재 비교 결과의 변경 심볼 하나를 기준으로 두 스냅샷을 다시 검증하고 분석한다. 입력·매핑·비교 설정을 바꾸면 먼저 **두 입력 비교**를 다시 실행해야 한다. 변경 지점이나 흐름 깊이를 바꾸면 **흐름 해석**을 다시 누르기 전까지 이전 해석과 다운로드를 숨긴다. 버전 선택과 표시 토글은 이미 만든 해석을 보여주며 분석을 반복하지 않는다.

- **Ver.A / Ver.B:** 반환값, 호출 결과, 변수 대입, 명시 호출 인자·매개변수, 표현식 의존, 조건 사용과 속성·첨자 쓰기 후보를 그래프로 표시한다. 그래프는 드래그·확대가 가능하다. 화살표는 코드의 의존 방향이며 시간 순서나 실행을 보장하지 않는다.
- **연결 근거:** 표의 연결을 선택하면 파일·줄·심볼, Python 표현식과 규칙에 따른 해석을 확인한다.
- **값이 연결되는 지점:** 변경 지점부터 상태 쓰기·조건·외부 호출·마지막 반환까지 이어지는 대표 경로를 실제 심볼·변수 이름으로 풀어 표시한다. 최대 8개·24단계이며 모든 경로를 나열하지 않는다.
- **호출·참조 관계도 함께 표시:** 기본값은 값 의존 연결만 표시한다. 토글을 켜면 기존 호출·참조 후보를 점선으로 함께 보여준다. 참조만으로 값이 전달됐다고 해석하지 않는다.
- **연결 차이:** Ver.B에서 추가된 연결, Ver.A에서 삭제된 연결, 공통 연결의 수와 근거를 표시한다. 계산식이 바뀌어도 연결 구조는 같을 수 있다. 연결 ID는 심볼·문장 종류/순서·호출 문맥 기준이므로 문장 삽입·삭제는 연결 대응에도 영향을 준다.
- **연결된 기능·TC:** 기존 매핑의 진입점마다 호출·참조 근거와 해당 코드 범위에 값 전달 근거가 생겼는지 구분한다. 진입점에 연결됐다는 사실만으로 화면 변경·영속 저장·기능 성공을 확정하지 않는다. TC 결과는 미실행이다.
- **추적이 멈춘 부분 / 분석 범위·확인 사항:** 동적 연결 등 지원 범위 밖의 표현식, 파싱 오류, 재귀와 깊이·노드 제한을 표시한다. 해석 JSON과 Markdown을 내려받을 수 있다.

직선적인 Python 문장과 명시 함수 호출을 우선 지원한다. 재대입하면 이전 값의 전달을 끊고, 호출 위치별 인자를 분리한다. 단순한 지역 클래스 생성 후 메서드 호출은 후보로 해석하지만 상속·데코레이터·동적 속성 등이 있으면 추적을 제한한다. 분기·루프·예외·context 본문, 단락 평가, comprehension, async/generator/decorator, 확장·가변 인자, heap 읽기·별칭과 전역/nonlocal 값은 추적 경계다. 추적 깊이는 1~30, 버전별 노드는 최대 160개다. LLM·RAG와 분석 대상 코드 실행은 사용하지 않는다.

상위 호출자 발견은 기존 보수적인 호출그래프 범위다. 그 그래프에서 찾지 못한 인스턴스·별칭·동적 callback 호출자를 새로 발견하지는 않는다. 지역 생성자 추정은 이미 도달한 코드 범위의 후속 값 전달에서 사용하며, receiver가 별칭이나 함수 인자로 전달되면 이후 메서드 타입 추적을 중단한다. 따라서 연결이 표시되지 않은 경우에도 실제 연결이 있을 수 있다.

APK·IPA 파일 구성 비교에서는 이 탭의 흐름 해석을 실행할 수 없다. 원본 Python 소스가 필요하다.

## 비교 범위

| 입력 쌍 | 결과 |
|---|---|
| Python 원본 ↔ Python 원본, Git ↔ 로컬 포함 | AST 변경·호출/참조 근거·매핑된 기능과 TC 후보 |
| 원본 프로젝트 ↔ 원본 프로젝트 | 상대 경로·파일 크기·SHA-256 변경 |
| APK ↔ APK | 패키지 파일 구성 변경 |
| IPA ↔ IPA | 패키지 파일 구성 변경·각 입력의 Info.plist 선언 메타데이터 |
| APK/IPA ↔ Git 원본, APK ↔ IPA | 직접 비교 차단·필요한 입력 안내 |

Git 소스와 패키지를 비교하려면 해당 Git 버전을 같은 빌드 설정으로 만든 패키지 또는 양쪽 원본 프로젝트가 필요하다. 현재 패키지에서 원본 코드를 자동 복원하거나 기능을 확정하지 않는다. 웹 화면에서는 임의 실행 도구/JADX 경로를 받지 않는다.

APK의 바이너리 AndroidManifest.xml을 해석하지 않는다. IPA 메타데이터는 선언 정보이며 서명·설치·실행 검증은 수행하지 않는다. 엔진을 실행하지 않는다. 세부 한계는 [`CONVERSION_GUIDE.md`](../AST/CONVERSION_GUIDE.md), [`COMPARISON_GUIDE.md`](../AST/COMPARISON_GUIDE.md)를 참고한다.

## 저장과 운영

각 브라우저 세션의 입력·변환 결과는 streamlit의 `.web_runs/session-...`에 격리된다. 원본 코드를 import/실행하지 않는다. 업로드 ZIP은 경로 이탈·링크·중복 경로와 크기 제한을 검사한다. 전체 스냅샷 ZIP 다운로드는 내용 합계/최종 ZIP 모두 최대 100MiB이며, 절대 서버 경로를 보관용 manifest에서 정리한다. 원본 입력의 다운로드·분석 보고서에는 사용자가 지정한 출처가 남을 수 있다.

분석이 끝나면 사이드바의 **세션 데이터 정리**를 누른다. 현재 브라우저 세션의 서버 입력 복사본·임시 Git 저장소·스냅샷·AST 보고서를 삭제하고 분석 결과와 다운로드 상태를 초기화한다. 세션 소유 표시와 절대 경로를 검증하며 링크가 있는 폴더는 삭제를 거부한다. 원본 파일·Git 저장소와 다른 세션은 보존한다. 필요한 결과는 먼저 내려받아야 한다. 브라우저 새로고침만으로 서버 파일 삭제가 확인되지는 않는다.

작업 검증용 임시 데이터는 검증 완료 후 삭제한다. 검증에 사용한 서버 세션, 별도 로컬 임시 폴더, 확인용 다운로드·화면 캡처를 정리하고 테스트 통과 수와 확인 범위는 문서에 기록한다. 저장소의 재사용 가능한 자동 테스트 코드·fixture와 사용자의 원본·최종 산출물은 임시 데이터와 구분한다. `Test/ast_compare_fixture.py`는 업데이트마다 다시 쓰는 지속 fixture이므로 삭제 대상이 아니다.

로컬 실행의 기본 주소는 localhost이고, 공개 호스팅은 위 Streamlit Cloud 주소를 사용한다. 공유 서버에서는 `QA_WEB_ALLOW_LOCAL=0`으로 로컬 파일·저장소 입력을 끄고 `QA_WEB_WORKSPACE`에 세션 보관 폴더를 지정한다. 앱 자체의 인증·업로드/복제 요청 제한·저장 용량/보관 기간 관리는 별도로 필요하다. 세션 폴더는 자동 삭제하지 않으며 현재 세션 정리 버튼 또는 서버를 멈춘 뒤 운영자의 정리를 사용한다.

## 검증

일반 업데이트에서는 변경 기능과 직접 연결된 테스트만 실행한다. 전체 회귀 테스트는 사용자 요청이 있을 때 AST 코어와 Streamlit 웹 프로젝트에 각각 실행한다.

```powershell
cd C:\codes\QA_train\AST
uv sync
.\.venv\Scripts\python.exe -X utf8 -B -m unittest discover -s tests -v

cd C:\codes\QA_train\streamlit
uv sync
.\.venv\Scripts\python.exe -X utf8 -B -m unittest discover -s tests -v
```

APK/IPA 테스트 fixture는 설치 가능한 실제 앱이 아닌 합성 ZIP이다.

Git 비교 기능의 기본 확인은 `git log --oneline -- Test/ast_compare_fixture.py`에서 이 파일의 기준·대상 커밋을 골라 진행한다. 비교 루트는 `Test`로 지정한다. 새 테스트 파일을 매번 만들고 삭제하지 않으며 비교 시나리오 자체가 바뀔 때만 `FIXTURE_REVISION`과 통제된 코드 구간을 수정한다.
